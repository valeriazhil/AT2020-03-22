## 1. Назначение и границы проекта

### 1.1. Цель

Создать веб-систему, объединяющую:

- **Helpdesk**: приём обращений по e-mail, автоматическое создание тикетов, работа с тикетами (ответы клиенту прямо из тикета, внутренние комментарии, статусы, назначение, вложения);
- **CRM-lite** («половина CRM»): карточки компаний и контактных лиц, частные клиенты, история взаимодействия, привязка тикетов;
- **Сервисный блок**: сторонние треки с ремонтными мастерскими/поставщиками и выдача техникам актуальных инструкций по типу устройства (архив документов, ZIP-пакеты, автоответ).

### 1.2. Исходные требования заказчика (Paul)

| # | Требование (оригинал) | Где покрыто в ТЗ |
|---|---|---|
| R1 | «half CRM + tickets» | разд. 5, 7 |
| R2 | get mails, create tickets, add comments, answer mails directly | разд. 5, 6 |
| R3 | add and edit contact info for company and contact persons | разд. 7 |
| R4 | a mail to ticket or support should autocreate a ticket | разд. 6.4 |
| R5 | attach files, links for file server, embed pictures | разд. 9 |
| R6 | single contacts for private customers | разд. 7.2 |
| R7 | companies with multiple contacts | разд. 7.1 |
| R8 | side tracks for repair shops / connected supply companies | разд. 8 |
| R9 | device specific instruction material as box for technicians, as auto reply | разд. 10, 12.4 |
| R10 | select a device type → zip with pictures/pdf from archive with current info | разд. 10.4 |
| R11 | maybe based on Nextcloud or similar | разд. 11 |

### 1.3. Что НЕ входит в первую версию (out of scope)

- Продажи/воронки сделок, счета, склад, бухгалтерия.
- Телефония, чат-виджет, мессенджеры (WhatsApp/Telegram) — заложить расширяемость каналов, реализовать позже.
- Клиентский портал самообслуживания — этап 3 (опционально).
- Мобильное приложение — только адаптивный веб-интерфейс.

## 2. Термины

| Термин | Определение |
|---|---|
| **Тикет** | Обращение клиента/внутренняя задача с номером, статусом, историей переписки. |
| **Агент** | Сотрудник поддержки/техник, работающий с тикетами. |
| **Группа** | Команда агентов (например, «1-я линия», «Техники», «Склад/RMA»). |
| **Почтовый ящик (канал)** | Адрес, с которого принимаются письма и отправляются ответы (support@, service@, rma@). |
| **Ответ (Reply)** | Публичное сообщение, уходящее клиенту по e-mail. |
| **Внутренняя заметка (Note)** | Комментарий, видимый только агентам. |
| **Компания** | Юр. лицо-клиент, у которого может быть несколько контактов. |
| **Контакт** | Физ. лицо: сотрудник компании или частный клиент (без компании). |
| **Партнёр** | Ремонтная мастерская, поставщик, сервисный подрядчик. |
| **Сторонний трек (Side track)** | Отдельная ветка переписки/задача с партнёром внутри тикета клиента. |
| **Тип устройства / модель** | Элемент каталога оборудования, к которому привязаны документы. |
| **Пакет инструкций** | Набор актуальных файлов по модели устройства, выдаваемый ZIP-архивом или ссылкой. |
| **SLA** | Нормативы времени первого ответа и решения. |
| **Шаблон ответа (Canned response)** | Заготовленный текст ответа с подстановками. |

## 3. Роли и права доступа

Модель RBAC: роль = набор прав; агенту назначается роль + одна или несколько групп.

| Роль | Права |
|---|---|
| **Администратор** | Всё: настройки, почтовые ящики, пользователи, роли, поля, автоматизации, хранилище, удаление данных, экспорт. |
| **Супервизор** | Все тикеты своих групп, переназначение, отчёты, шаблоны, правила SLA групп, слияние тикетов, управление каталогом устройств. |
| **Агент поддержки** | Тикеты своих групп (или все — настраивается), ответы, заметки, создание/редактирование контактов и компаний, создание сторонних треков. |
| **Техник** | Назначенные тикеты, заметки, чтение CRM, доступ к библиотеке инструкций, отправка пакетов инструкций. Ответ клиенту — настраиваемое право. |
| **Только чтение** | Просмотр тикетов и CRM без изменений (руководство, бухгалтерия). |
| **Менеджер библиотеки** | Загрузка/версионирование документов по устройствам, публикация пакетов. |

Требования:

- Видимость тикетов: «все», «только группы агента», «только назначенные мне».
- Право на удаление тикетов/контактов — отдельно, по умолчанию только Администратор (удаление «мягкое», с корзиной на 30 дней).
- Все изменения пишутся в журнал аудита (кто, когда, что было → что стало).
- Аутентификация: логин/пароль + 2FA (TOTP); опционально SSO (OIDC/LDAP/Active Directory, Microsoft Entra ID).

## 5. Модуль «Тикеты»

### 5.1. Способы создания тикета

1. Автоматически из входящего письма на подключённый ящик (разд. 6).
2. Вручную агентом (например, по телефонному звонку) — с выбором/созданием контакта.
3. «Исходящее письмо» — агент пишет клиенту первым, создаётся тикет со статусом «Ожидание».
4. Через REST API / веб-форму на сайте (этап 2).
5. Из карточки контакта/компании (кнопка «Новый тикет»).

### 5.2. Поля тикета

Стандартные:

| Поле | Тип | Примечание |
|---|---|---|
| Номер | авто, уникальный | Формат настраиваемый, например `#10234` или `SUP-2026-00123` |
| Тема | строка | Из темы письма |
| Описание | rich-text | Первое сообщение |
| Запрашивающий (контакт) | ссылка на контакт | Обязательно |
| Компания | ссылка | Подставляется из контакта, можно изменить |
| Статус | список | см. 5.3 |
| Приоритет | список | Низкий / Средний / Высокий / Срочный |
| Тип | список | Вопрос, Неисправность, Ремонт/RMA, Установка, Рекламация, Заказ запчастей (настраиваемый) |
| Источник | авто | E-mail, Телефон, Портал, API, Вручную |
| Группа | ссылка | |
| Ответственный агент | ссылка | |
| Наблюдатели (watchers) | список агентов | Получают уведомления |
| CC | список e-mail | Из письма, копии клиента |
| Теги | список | |
| Модель устройства | ссылка на каталог | Нужна для пакетов инструкций |
| Серийный номер | строка | |
| Срок первого ответа / решения | авто (SLA) | Можно изменить вручную с правом |
| Связанные тикеты | ссылки | |

Пользовательские поля (конструктор в настройках): текст, многострочный текст, число, дата, флажок, выпадающий список, зависимые списки (Категория → Подкатегория → Причина), ссылка на запись CRM. Для каждого поля: обязательность при закрытии, видимость по типу тикета.

### 5.3. Статусы (жизненный цикл)

| Статус | Значение | SLA-таймер |
|---|---|---|
| **Новый** | Создан, никто не взял | идёт |
| **Открыт** | В работе у агента | идёт |
| **Ожидание клиента** | Задан вопрос клиенту | на паузе |
| **Ожидание партнёра** | Активен сторонний трек (мастерская/поставщик) | на паузе (настраиваемо) |
| **Решён** | Решение предложено | остановлен |
| **Закрыт** | Окончательно закрыт (авто через N дней после «Решён») | — |

Правила:

- Ответ клиента в «Ожидание клиента»/«Решён» → автоматически «Открыт».
- Ответ клиента на «Закрыт» тикет → либо переоткрыть (если прошло < N дней, настраивается), либо создать новый тикет со ссылкой на старый.
- Администратор может добавлять собственные статусы с указанием, останавливают ли они SLA.

### 5.4. Действия с тикетом

- **Ответить** (публично, уходит e-mail), **Ответить всем**, **Переслать** (третьему лицу, переписка сохраняется в тикете).
- **Внутренняя заметка** с @упоминанием агента (уведомление упомянутому).
- Смена любых свойств, история изменений в ленте.
- **Слияние** тикетов (дубликаты от одного клиента): переписка переносится в основной, дочерние закрываются со ссылкой.
- **Разделение**: выделить сообщение в новый тикет.
- **Связанные тикеты** и **родитель-потомок** (например, одна поставка → несколько ремонтов).
- **Сторонний трек** (разд. 8).
- **Отправить инструкции** (разд. 10).
- **Применить сценарий** (макрос: набор действий одной кнопкой).
- **Время работы**: учёт затраченного времени (таймер/ручной ввод) — опционально, этап 2.
- **Печать / экспорт в PDF** тикета с перепиской.
- Пометить как спам, заблокировать отправителя.

### 5.5. Распределение тикетов

- Ручное назначение.
- Правила автоматизации по условиям (ящик, домен отправителя, ключевые слова, компания, тип устройства).
- Round-robin внутри группы с учётом доступности агента и лимита открытых тикетов (этап 2).

## 6. Интеграция электронной почты (подробно)

Это ключевой модуль. Реализовать по образцу Freshdesk: каждый почтовый ящик поддержки — это «канал», письма в который превращаются в тикеты, а ответы агентов уходят от имени этого ящика.

### 6.1. Варианты подключения ящика

Администратор в **Настройки → Каналы → Почтовые ящики → Добавить** выбирает способ:

| Способ | Как работает | Когда использовать |
|---|---|---|
| **A. IMAP + SMTP (рекомендуемый базовый)** | Система сама забирает письма с почтового сервера по IMAP и отправляет через SMTP этого же сервера. | Любой почтовый хостинг, собственный сервер (Postfix/Dovecot, Exchange с IMAP). |
| **B. Microsoft 365 / Exchange Online** | OAuth2 (Microsoft Entra ID), чтение через Microsoft Graph API или IMAP с XOAUTH2, отправка через Graph `sendMail` или SMTP с XOAUTH2. | Если почта в Microsoft 365 — Basic Auth там отключена, нужен OAuth2. |
| **C. Google Workspace / Gmail** | OAuth2, Gmail API (или IMAP/SMTP с XOAUTH2). | Если почта в Google. |
| **D. Переадресация (forwarding)** | Почтовый сервер клиента пересылает письма на служебный адрес системы (например, `support@inbound.ourcrm.local`), система принимает их встроенным SMTP-приёмником / через webhook почтового сервиса. Отправка — через SMTP. | Когда нельзя дать системе доступ к ящику. Аналог Freshdesk-адреса `xxx@company.freshdesk.com`. |

Требование: варианты A и D — в MVP; B и C — в MVP, если почта заказчика в M365/Google (уточнить, см. разд. 24).

### 6.2. Параметры почтового ящика (форма настройки)

- Название канала (например, «Поддержка», «Сервис/RMA»).
- E-mail адрес ящика, имя отправителя («Сервис компании X»).
- **Входящая почта**: хост, порт (993), шифрование (SSL/TLS / STARTTLS), логин, пароль или OAuth2, папка для чтения (INBOX), действие после обработки: *пометить прочитанным* / *переместить в папку «Processed»* / *удалить* (по умолчанию — переместить).
- **Исходящая почта**: хост, порт (587/465), шифрование, логин/пароль/OAuth2.
- Группа по умолчанию для новых тикетов из этого ящика, приоритет и тип по умолчанию.
- Подпись по умолчанию.
- Кнопка **«Проверить подключение»** (тест IMAP и SMTP, отправка тестового письма).
- Флажок «Активен».

Пароли/токены хранятся в БД зашифрованно (AES-256, ключ вне БД).

### 6.3. Получение писем (технически)

1. Фоновый воркер для каждого ящика:
   - IMAP: держит соединение **IMAP IDLE** (мгновенная доставка) + резервный опрос каждые 1–2 минуты; запоминает `UIDVALIDITY`/`UID` последнего обработанного письма.
   - Graph/Gmail API: подписка на уведомления (webhook/push) + периодический опрос дельты.
   - Forwarding: встроенный приёмник SMTP или HTTP-webhook от почтового шлюза.
2. Исходное письмо (raw `.eml`) сохраняется в хранилище **до** разбора — для отладки и повторной обработки.
3. Каждое письмо ставится в очередь задач; обработка идемпотентна по `Message-ID` (дубликат не создаёт второй тикет).
4. Ошибки разбора не теряют письмо: оно попадает в раздел «Необработанные письма» с возможностью повторить/создать тикет вручную.

### 6.4. Алгоритм «письмо → тикет» (mail-to-ticket)

```
Входящее письмо
   │
   ├─ 1. Фильтры: блок-лист, спам-оценка, правила игнорирования ─► Спам/Игнор
   │
   ├─ 2. Защита от петель: Auto-Submitted ≠ no, Precedence: bulk/auto_reply,
   │     X-Autoreply, отправитель = наш же ящик, лимит N писем/час от адреса
   │     ─► сохраняем как заметку/игнор, автоответ НЕ отправляем
   │
   ├─ 3. Это ответ в существующий тикет? (по порядку)
   │     a) In-Reply-To / References совпадает с Message-ID наших писем
   │     b) В теме есть маркер тикета: [#10234] или [SUP-2026-00123]
   │     c) (опц.) скрытый токен в теле/адресе reply-to (support+t10234@...)
   │     ─► ДА: добавить сообщение в тикет, сменить статус по правилам
   │           (если это ответ партнёра — в сторонний трек, разд. 8)
   │
   ├─ 4. Определить контакт по From:
   │     ─ найден → берём контакт и его компанию
   │     ─ не найден → создать контакт; если домен e-mail привязан
   │       к компании (поле «домены компании») → привязать к компании,
   │       иначе — частный клиент
   │
   ├─ 5. Создать тикет: тема, тело (HTML очищенный + текст), вложения,
   │     inline-картинки, CC, канал, группа/приоритет по умолчанию
   │
   ├─ 6. Правила автоматизации «при создании» (разд. 12)
   │
   └─ 7. Автоответ клиенту «Ваше обращение #10234 принято» (если включён
         и не сработала защита от петель)
```

Детали разбора:

- Поддержка `multipart/alternative`, `multipart/mixed`, `multipart/related`, кодировки (UTF-8, ISO-8859-x, Windows-1251/1252), `quoted-printable`, `base64`, RFC 2047 в заголовках.
- HTML письма **санитизируется** (удаление `<script>`, обработчиков событий, внешних форм; внешние картинки — загрузка по клику «Показать картинки» для защиты от трекинга).
- Inline-картинки (`cid:`) сохраняются как вложения и отображаются в теле.
- Вложенные письма (`message/rfc822`, `.eml`, `.msg` из Outlook) — сохраняются как вложение, с просмотром.
- Отделение цитируемой части («-----Original Message-----», `>`-цитаты, «Am ... schrieb ...:», «On ... wrote:») — сворачивается в интерфейсе, но не удаляется.
- Если письмо пришло сразу на несколько наших ящиков — один тикет (дедупликация по `Message-ID`).
- Письма на адреса в CC добавляются в CC тикета.
- Максимальный размер письма — настраиваемый (по умолчанию 50 МБ), превышение — тикет создаётся, вложение помечается «не загружено», администратор уведомляется.

### 6.5. Отправка ответов из тикета

- Отправитель — ящик канала, через который пришёл тикет (можно выбрать другой из разрешённых).
- Тема: `Re: <тема> [#10234]` — маркер тикета обязателен для надёжного треддинга.
- Заголовки: собственный `Message-ID` (`<ticket-10234-msg-5678@наш-домен>`), `In-Reply-To` и `References` — на последнее письмо клиента, чтобы почтовые клиенты (Outlook, Gmail) группировали переписку.
- `Reply-To` — адрес ящика (опционально с plus-адресацией `support+t10234@`).
- Для автоматических писем (автоответ, уведомления) — `Auto-Submitted: auto-replied` / `auto-generated`.
- Подпись агента/канала, цитирование предыдущей переписки (настраивается: «включать историю» да/нет).
- Вложения из ПК, из других сообщений тикета, из библиотеки инструкций, ссылкой (разд. 9, 10).
- Отправка асинхронная через очередь; статус в ленте: «В очереди → Отправлено → Ошибка (причина, кнопка «Повторить»)».
- Отложенная отправка и «отмена отправки» в течение 10 секунд — этап 2.
- Отправленные письма опционально копируются в папку «Отправленные» ящика по IMAP (`APPEND`), чтобы в почтовом клиенте была полная картина.

### 6.6. Доставляемость (обязательно для ИТ-администратора заказчика)

- SPF: разрешить сервер, с которого уходит почта.
- DKIM: подпись исходящих писем (на стороне почтового сервера или системой).
- DMARC: политика домена.
- Если используется forwarding (вариант D) — отправка всё равно через SMTP домена заказчика, чтобы письма не попадали в спам.

### 6.7. Ошибки доставки (bounce)

- Входящие NDR/bounce (`multipart/report`, `Content-Type: message/delivery-status`) распознаются, привязываются к исходному сообщению, в тикете отображается «Письмо не доставлено: <причина>», агенту — уведомление.
- Адрес контакта с постоянными ошибками помечается «недоставляемый».

### 6.8. Ручной импорт

- Перетащить `.eml`/`.msg` файл в систему → создать тикет или добавить в существующий (для писем, пришедших на личные ящики сотрудников).
- (Этап 2) Надстройка для Outlook / пересылка на ящик с правилом «создать тикет от имени исходного отправителя» (распознавание пересланного письма агентом).

## 8. Сторонние треки (ремонтные мастерские, поставщики)

Цель: внутри тикета клиента вести отдельную переписку/задачу с внешней организацией (мастерская, поставщик запчастей, сервисный подрядчик), не смешивая её с перепиской клиента. Аналог в Freshdesk — «child tickets / linked tickets» и «Freshdesk Contact Center/Field service tasks»; здесь реализуем как специализированную сущность.

### 8.1. Справочник партнёров

Раздел меню **«Партнёры»**: компания-партнёр (тип: ремонтная мастерская / поставщик / перевозчик / подрядчик), контакты, e-mail для треков, адрес приёма оборудования, нормативный срок ремонта/ответа, специализация (какие модели устройств обслуживает), заметки.

### 8.2. Создание трека

В тикете кнопка **«Сторонний трек +»**:

- Выбор партнёра (с подсказкой по модели устройства из тикета) и контакта партнёра.
- Тип трека: Ремонт / Заказ запчасти / Запрос информации / Выезд / Возврат (RMA).
- Тема (по умолчанию: `[#10234-T1] Ремонт XR-200 SN 12345`), текст, вложения (можно выбрать вложения из тикета клиента).
- Опционально: срок, ответственный агент, номер RMA/заказа у партнёра, трек-номер отправки, стоимость.

### 8.3. Поведение

- У трека свой номер (`#10234-T1`, `#10234-T2`), статус (Создан → Отправлено партнёру → В работе у партнёра → Ожидает нас → Завершён / Отменён) и своя лента переписки.
- Письма партнёру уходят из системы; ответы партнёра распознаются по маркеру `[#10234-T1]` и заголовкам (разд. 6.4) и попадают **в трек, а не клиенту**.
- Клиент переписку трека не видит. Агент может кнопкой «Поделиться с клиентом» процитировать сообщение партнёра в ответе клиенту.
- Пока есть открытые треки, тикет может автоматически быть в статусе «Ожидание партнёра» (настраиваемо).
- Завершение трека → уведомление ответственному агенту тикета, внутренняя системная запись в ленте.
- Напоминание партнёру/агенту при превышении срока трека (автоматизация по времени).
- Список **«Тикеты → Сторонние треки»**: все треки с фильтрами по партнёру, статусу, просрочке.
- Отчёт: среднее время ремонта по партнёрам, количество треков.

### 8.4. Этап 3 (опционально)

Партнёрский портал: партнёр логинится и видит только свои треки, меняет статус, загружает акты.

## 9. Вложения, ссылки на файловый сервер, картинки

### 9.1. Вложения

- Загрузка: кнопка, drag-and-drop, вставка из буфера (Ctrl+V скриншота).
- Ограничения настраиваемые: макс. размер файла (по умолчанию 25 МБ для e-mail, 2 ГБ для внутреннего хранения), запрещённые расширения (`.exe`, `.bat`, `.js` и т.п.).
- Антивирусная проверка (ClamAV) всех входящих и загружаемых файлов; заражённые — в карантин.
- Просмотр в браузере: изображения, PDF, видео, текст; остальное — скачивание.
- Вложения тикета собраны в отдельной вкладке «Файлы тикета».
- Если суммарный размер вложений к письму превышает лимит почты (настраиваемо, напр. 20 МБ) — система предлагает отправить **ссылку на скачивание** с ограниченным сроком действия вместо файла.

### 9.2. Ссылки на файловый сервер

- Кнопка **«Ссылка на файл»** в редакторе: агент вставляет путь/URL (`\\fileserver\service\XR-200\...`, `smb://...`, `https://nextcloud.../s/...`).
- Тип ссылки: внутренняя (видна только агентам в заметках) / внешняя (для клиента — только HTTP(S)-ссылки).
- Ограничение: браузеры не открывают `smb://` и UNC-пути напрямую — для внутренних путей предусмотреть кнопку «Копировать путь»; для удобства рекомендуется публиковать файл-сервер через Nextcloud/WebDAV (разд. 11), тогда ссылка открывается в браузере.
- При интеграции с Nextcloud — выбор файла через диалог-браузер хранилища и создание публичной ссылки (share link) с паролем/сроком действия одним кликом.

### 9.3. Встроенные картинки

- В редакторе ответов/заметок: вставка картинки из буфера, drag-and-drop в текст, изменение размера.
- При отправке e-mail картинки встраиваются как `inline` (`Content-ID`), а не как внешние ссылки — чтобы отображались у клиента без загрузки внешнего контента.
- Входящие inline-картинки отображаются в ленте на своих местах.

## 10. Каталог устройств и пакеты инструкций

### 10.1. Цель

Техник/агент выбирает модель устройства — система прикладывает к ответу (или отправляет автоответом) **актуальный** комплект материалов: инструкции по установке, ремонту, фото, схемы, прошивки, — из единого архива с версионированием.

### 10.2. Каталог устройств (меню «Устройства и инструкции → Каталог»)

Иерархия:

```
Категория (напр. «Контроллеры»)
 └ Производитель
    └ Тип / серия (XR)
       └ Модель (XR-200)
          └ Модификация / ревизия (XR-200 rev.B) — опционально
```

Поля модели: название, артикул, изображение, статус (актуальна / снята с производства), аналоги, совместимые запчасти (этап 2), ответственный за документацию.

### 10.3. Библиотека документов

- Документ привязывается к одной или нескольким моделям (или ко всему типу/категории).
- Категории документов: Инструкция по установке, Руководство по ремонту, Сервисный бюллетень, Схема, Фото, Прошивка/ПО, Сертификат, Чек-лист.
- Атрибуты: язык (DE/EN/RU…), аудитория (**для клиента** / **только для техников**), версия, дата действия, статус (черновик / опубликован / устарел).
- **Версионирование**: загрузка новой версии делает её актуальной, старые хранятся в истории; в пакеты всегда попадает только опубликованная актуальная версия.
- Источник файла: собственное хранилище или папка Nextcloud (разд. 11) — с синхронизацией.

### 10.4. Пакеты инструкций

**Пакет** = правило «какие документы собрать для модели», например «Пакет установки XR-200 (DE)»: категории «Установка» + «Фото» + «Чек-лист», язык DE, аудитория «для клиента».

Использование в тикете — кнопка **«Отправить инструкции»** (или в редакторе «Пакет»):

1. Модель подставляется из поля тикета (или выбирается).
2. Выбор пакета (или ручная отметка файлов), языка.
3. Предпросмотр списка файлов с версиями и суммарным размером.
4. Способ доставки:
   - **ZIP-вложение** — система собирает архив `XR-200_Installation_DE_2026-11-19.zip` на лету;
   - **ссылка** на скачивание (рекомендуется для > 10–20 МБ) — с ограниченным сроком (напр. 14 дней) и опционально паролем;
   - отдельными файлами.
5. Текст письма из шаблона пакета (с подстановками: имя клиента, модель, номер тикета).
6. В ленте тикета фиксируется, **какие файлы каких версий** были отправлены (для истории и претензий).

Требования:

- Сборка ZIP асинхронно; готовые ZIP кэшируются до изменения состава/версий пакета.
- Документы «только для техников» нельзя отправить клиенту (блокировка + предупреждение), только техникам/партнёрам.
- Отправка пакета партнёру из стороннего трека — разрешена (включая документы для техников, при наличии права).

### 10.5. Автоответ с инструкциями

Через автоматизации (разд. 12): например, «Если тип тикета = Установка и модель указана (или распознана по ключевым словам в теме/теле, например `XR-200`) → отправить пакет "Установка" автоматически». Варианты:

- полностью автоматически при создании тикета;
- как **предложение** агенту: в тикете появляется плашка «Рекомендуемый пакет: Установка XR-200 [Отправить]» — рекомендуемый режим для старта.

### 10.6. «Бокс техника»

На экране тикета в правой панели блок **«Материалы по устройству»**: список актуальных документов по модели тикета (включая «только для техников»), просмотр в браузере, скачивание, «Прикрепить к ответу/треку». Также отдельная страница библиотеки с поиском по модели — для работы техника вне тикета (в том числе с телефона на выезде).

## 11. Хранилище файлов: собственное или Nextcloud

### 11.1. Абстракция хранилища

В системе реализуется единый слой `StorageProvider` с драйверами:

| Драйвер | Использование |
|---|---|
| **Локальный диск / NFS** | Простая установка, малые объёмы. |
| **S3-совместимое хранилище (MinIO, собственный сервер)** | **Рекомендуется** для вложений писем и тикетов: масштабируемость, версионирование, lifecycle-политики. |
| **Nextcloud (WebDAV + OCS Share API)** | Для библиотеки документов по устройствам и ссылок для клиентов/партнёров. |

### 11.2. Рекомендуемая схема

- **Вложения тикетов и сырые письма** — собственное S3/MinIO-хранилище (быстро, под контролем системы, не зависит от структуры папок).
- **Библиотека инструкций** — два варианта на выбор заказчика:
  1. *Nextcloud как источник истины*: сотрудники ведут документы в привычных папках Nextcloud по шаблону `/Service-Library/<Категория>/<Производитель>/<Модель>/<Тип документа>/`; система синхронизирует индекс (через WebDAV `PROPFIND` по расписанию или по уведомлениям), берёт файлы для пакетов, создаёт share-ссылки через OCS API (`/ocs/v2.php/apps/files_sharing/api/v1/shares`) со сроком действия и паролем.
  2. *Собственная библиотека*: документы загружаются в систему (S3), версионирование и публикация — внутри системы; Nextcloud не нужен.
- Подключение Nextcloud — через отдельного служебного пользователя с app-password, только к нужной папке.

### 11.3. Требования

- Резервное копирование хранилища и БД — ежедневно, хранение 30 дней, проверка восстановления.
- Шифрование при передаче (TLS) и рекомендовано — на диске.
- Доступ к файлам только через систему с проверкой прав (подписанные временные URL), без публичных бакетов.
- Квоты и отчёт по занятому месту.

## 12. Автоматизации, SLA, шаблоны ответов

Модель по образцу Freshdesk.

### 12.1. Правила «при создании тикета» (Dispatcher)

Выполняются по порядку для каждого нового тикета. Конструктор «ЕСЛИ (условия) → ТО (действия)».

- Условия: ящик/канал, отправитель, домен, тема/тело содержит, компания, уровень обслуживания, язык, время (рабочее/нерабочее), наличие вложений, распознанная модель устройства.
- Действия: назначить группу/агента, установить приоритет/тип/теги/поля, отправить e-mail (клиенту/агенту/группе), отправить пакет инструкций или предложить его, пометить спамом, удалить, добавить наблюдателя, вызвать webhook.

Примеры:

- Письмо на `rma@` → тип «Ремонт/RMA», группа «Техники».
- Компания с уровнем «Премиум» → приоритет «Высокий».
- Тема содержит «срочно», «dringend», «urgent» → приоритет «Срочный».

### 12.2. Правила «при обновлении» (Observer)

События: ответ клиента, ответ агента, заметка, смена статуса/приоритета/агента, завершение стороннего трека, ответ партнёра. Те же условия и действия + «кто выполнил действие».

### 12.3. Правила по времени (Supervisor)

Запуск каждые 15–60 минут: «тикет в статусе "Ожидание клиента" > 5 дней → напомнить клиенту», «> 10 дней → Закрыть», «Решён > 3 дней → Закрыт», «трек партнёра просрочен → напомнить партнёру и агенту», «неназначен > 30 минут → уведомить супервизора».

### 12.4. Автоответы

- Подтверждение получения (с номером тикета) — для каждого ящика свой шаблон и язык.
- Сообщение в нерабочее время / праздники.
- Автоответ с пакетом инструкций (разд. 10.5).
- Защита от петель обязательна (разд. 6.4, шаг 2): не отвечать на автоответы, рассылки, свои ящики; не более 1 автоответа в N минут одному адресу.

### 12.5. SLA

- Политики: время первого ответа, время следующего ответа, время решения — по приоритету; условия применения (компания, уровень обслуживания, тип тикета, группа).
- Расчёт только в рабочие часы группы с учётом праздников; пауза в статусах ожидания.
- Эскалации: предупреждение до нарушения (напр. за 30 мин) и при нарушении — агенту, супервизору.

### 12.6. Шаблоны ответов и сценарии

- **Шаблоны ответов** (canned responses): папки, личные/общие, многоязычные варианты, плейсхолдеры `{{contact.first_name}}`, `{{ticket.id}}`, `{{ticket.device_model}}`, `{{agent.name}}`, вставка вложений из шаблона.
- **Сценарии (макросы)**: набор действий одной кнопкой, например «Отправить в ремонт»: тип = RMA, создать трек с мастерской X, шаблон ответа клиенту, статус «Ожидание партнёра».
- **Внутренняя база знаний** (этап 2): статьи-решения для агентов с поиском из тикета; публичная часть — для клиентского портала (этап 3).

## 17. Модель данных

Основные сущности (упрощённо):

```
Organization (настройки системы)
User (агент) ─┬─ Role
              └─ Group (M:N)

Mailbox (канал): адрес, IMAP/SMTP/OAuth, группа по умолч.

Company ── 1:N ── Contact (company_id NULL = частный клиент)
Company ── 1:N ── CompanyDomain, Address
Partner (тип) ── 1:N ── PartnerContact

Ticket
  ├ requester_id → Contact, company_id → Company
  ├ mailbox_id, group_id, assignee_id, status, priority, type
  ├ device_model_id → DeviceModel, serial_no
  ├ sla_policy_id, first_response_due, resolution_due
  ├ custom_fields (JSONB)
  ├ 1:N Message (reply / note / forward / system)
  │      ├ direction (in/out), from, to, cc, bcc, subject
  │      ├ body_html, body_text, message_id_header, in_reply_to, references
  │      ├ raw_eml_file_id, delivery_status
  │      └ 1:N Attachment → File
  ├ 1:N SideTrack (partner_id, status, type, due, rma_no)
  │      └ 1:N Message
  ├ M:N Tag, Watcher(User), LinkedTicket, parent_ticket_id
  └ 1:N TicketEvent (аудит изменений)

DeviceCategory → Manufacturer → DeviceType → DeviceModel
Document ── M:N ── DeviceModel
  └ 1:N DocumentVersion → File (storage_driver, path/key, checksum, size)
InstructionPackage (правило: модели, категории, язык, аудитория, шаблон)
PackageDelivery (ticket/sidetrack, список DocumentVersion, способ, ссылка, срок)

File (storage_driver: local|s3|nextcloud, key, mime, size, sha256, av_status)
CannedResponse, Macro, AutomationRule, SlaPolicy, BusinessHours, Holiday
CustomFieldDefinition (entity, type, options, required)
AuditLog, Notification, ApiKey, Webhook
```

Требования к данным:

- Все сущности: `created_at`, `updated_at`, `created_by`, мягкое удаление `deleted_at`.
- Номер тикета — отдельная последовательность, не равная внутреннему ID.
- Пользовательские поля — JSONB + определения полей (индексируемые).
- Хранение `Message-ID` всех входящих и исходящих писем с индексом — для треддинга.

## 20. Рекомендуемая архитектура и стек

```
[Браузер SPA] ⇄ HTTPS/WebSocket ⇄ [Backend API]
                                     │
           ┌─────────────────────────┼────────────────────────┐
     [PostgreSQL]           [Redis: очереди, кэш,    [Хранилище файлов:
     (данные, полнотекст     WebSocket pub/sub]       MinIO/S3 + Nextcloud]
      или OpenSearch)                │
                       ┌─────────────┴──────────────┐
               [Почтовые воркеры]         [Фоновые воркеры: автоматизации,
               IMAP IDLE / Graph / Gmail,  SLA, ZIP-пакеты, антивирус ClamAV,
               SMTP-отправка                синхронизация Nextcloud]
```

Варианты стека (выбрать по компетенциям команды):

- **Backend**: Python (Django/FastAPI + Celery) или Node.js (NestJS + BullMQ) или PHP (Laravel + Horizon), или Java (Spring Boot) — команда уже работает с Java.
- **Frontend**: React или Vue 3 + TypeScript; WYSIWYG-редактор (TipTap/ProseMirror) с поддержкой вставки картинок.
- **Почта**: проверенные библиотеки разбора MIME (Python `email`/`mail-parser`, Node `mailparser`/`imapflow`/`nodemailer`, Java Jakarta Mail); санитизация HTML — DOMPurify/bleach.
- **БД**: PostgreSQL 15+; поиск — PostgreSQL FTS на старте, OpenSearch/Meilisearch при росте.
- **Развёртывание**: Docker Compose (on-premise) или Kubernetes; обратный прокси Nginx/Traefik с Let's Encrypt.

## 21. Этапы реализации

### Этап 1 — MVP (обязательный функционал)

1. Пользователи, роли, группы, 2FA.
2. Подключение почтовых ящиков (IMAP/SMTP + OAuth2 для M365/Google при необходимости), forwarding.

4. Список и карточка тикета, статусы, приоритеты, назначение, теги, пользовательские поля, слияние.

6. Вложения, вставка картинок, ссылки на файлы, антивирус, S3/MinIO.
7. Шаблоны ответов, автоответ о получении, базовые автоматизации при создании.
8. Глобальный поиск, фильтры, уведомления в приложении и по e-mail.
9. Базовые отчёты, журнал аудита, бэкапы.

### Этап 2 — Сервисный блок

1. Партнёры и сторонние треки.
2. Каталог устройств, библиотека документов с версиями.
3. Пакеты инструкций (ZIP/ссылка), «бокс техника», рекомендации/автоответы с пакетами.
4. Интеграция с Nextcloud (синхронизация библиотеки, share-ссылки).
5. SLA с рабочими часами и эскалациями, правила при обновлении и по времени, сценарии (макросы).
6. Учёт времени, CSAT, база знаний для агентов, REST API + вебхуки.

### Этап 3 — Расширения (по решению заказчика)

Клиентский портал (мои тикеты, база знаний), партнёрский портал, установленная база устройств клиента с гарантией, веб-форма/чат, телефония, ERP-интеграция, мобильное приложение для техников.

## 22. Критерии приёмки

| # | Сценарий | Ожидаемый результат |
|---|---|---|
| A1 | Клиент пишет на support@ с нового адреса, с 2 вложениями и картинкой в теле | Создан тикет со всеми вложениями и картинкой на месте; создан контакт (частный или в компании по домену); клиенту ушёл автоответ с номером. |
| A2 | Агент отвечает из тикета | Клиент получает письмо от support@ с номером в теме; в Outlook/Gmail оно в той же цепочке. |
| A3 | Клиент отвечает на письмо агента (с изменённой темой) | Ответ попадает в тот же тикет (по In-Reply-To), статус → «Открыт», агенту уведомление. |
| A4 | Клиент отвечает, удалив заголовки, но оставив `[#10234]` в теме | Ответ попадает в тикет 10234. |
| A5 | На support@ приходит автоответ «Out of office» | Тикет не создаёт бесконечных автоответов; петли нет. |
| A6 | Агент создаёт сторонний трек к мастерской, мастерская отвечает | Ответ мастерской — в треке, клиент его не получает; тикет в статусе «Ожидание партнёра». |
| A7 | Техник нажимает «Отправить инструкции» для XR-200, пакет «Установка DE» | Клиенту ушёл ZIP (или ссылка) только с актуальными опубликованными версиями для клиента; в ленте зафиксированы файлы и версии. |
| A8 | В библиотеку загружена новая версия инструкции | Следующая отправка пакета содержит новую версию, история хранит старую. |
| A9 | Агент без права пытается отправить клиенту документ «только для техников» | Система блокирует отправку. |
| A10 | Компания с 3 контактами, у каждого по тикету | В карточке компании видны 3 контакта и 3 тикета. |
| A11 | Почтовый сервер недоступен 30 минут | После восстановления все письма загружены, дублей нет; администратор получил алерт. |
| A12 | Входящее письмо с `<script>` в HTML | Скрипт не выполняется (санитизация). |
| A13 | Удаление контакта по запросу GDPR | Персональные данные анонимизированы, тикеты остаются для статистики без ПДн. |

Тестирование: автотесты разбора почты на наборе реальных писем (Outlook, Gmail, Apple Mail, Thunderbird, мобильные клиенты, разные кодировки, `.msg`, вложенные письма, NDR); нагрузочный тест входящего потока; пентест перед запуском.

## 23. Альтернатива: доработка готового open-source решения

Прежде чем разрабатывать с нуля, рекомендуется оценить готовые self-hosted системы, покрывающие значительную часть этапа 1:

| Система | Что есть из коробки | Чего не хватает (дорабатывать) |
|---|---|---|
| **Zammad** (AGPL) | Mail-to-ticket, треддинг, M365/Google OAuth, организации и пользователи, триггеры, SLA, шаблоны, база знаний, REST API, отчёты | Каталог устройств и пакеты инструкций, сторонние треки как сущность, интеграция Nextcloud для пакетов |
| **FreeScout** (AGPL, PHP/Laravel) | Shared inbox «как Help Scout», модули (платные/бесплатные): CRM-поля, вложения, шаблоны | Полноценные компании/SLA частично через модули; сервисный блок — разработка модуля |
| **osTicket** (GPL) | Почта → тикеты, SLA, поля | Устаревший интерфейс, слабая CRM |

Рекомендация: провести пилот Zammad (2–3 почтовых сценария из разд. 22) и сравнить стоимость доработки сервисного блока (разд. 8, 10, 11) как плагина/внешнего микросервиса через API с разработкой собственной системы. Решение фиксируется до старта этапа 1.

## 24. Открытые вопросы к заказчику

1. Где размещена почта (собственный сервер, Microsoft 365, Google Workspace, хостинг)? Сколько ящиков подключать (support@, service@, rma@…)?

3. Нужен ли перенос старой переписки/контактов? Из какого источника (Outlook, Excel, другая CRM)?
4. Языки клиентов и интерфейса (DE/EN/RU/другие)?
5. Хостинг: on-premise (свой сервер) или облако в ЕС?
6. Есть ли уже Nextcloud и структура папок с инструкциями? Кто будет вести библиотеку документов?
7. Сколько моделей устройств и примерный объём документации (ГБ)?

11. Нужны ли интеграции с ERP/бухгалтерией/телефонией и в каком этапе?
12. Требования к SSO (Active Directory / Entra ID)?
13. Срок хранения данных и требования юриста по GDPR?
14. Строим своё или берём за основу open-source (разд. 23)?
